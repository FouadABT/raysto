# Raysto product direction

**Conversation integration — 26 October 2026:** the approved Road to 10/10 milestone now connects native visit rooms, real Gemini tools, exact Sandbox shares and the Next.js AG Grid/AG Studio console at ops.rays.to. Earlier web exclusions describe older phases. See [current status](project-status.md) and [release evidence](road-to-10-10.md); buyer approval, remote MCP access and device/pilot gates remain open.

**Mobile art direction — 26 October 2026:** version 0.10.0 adds original dining artwork, six native vector scenes, an adaptive spring dock, illustrated connected journeys and the matching explicit offline-demo surfaces. Functional integration remains intact. See [mobile-art-direction.md](mobile-art-direction.md) and its screen review. The current phase permits the focused validation and Android build described there; historical test deferrals below do not apply to this release.

**Mobile integration — 26 October 2026:** the current authorized phase connects the native Flutter product to the deployed v2 restaurant backend. Connected discovery, orders, dining, kitchen/courier operations, media/AI, management and administration use server-owned records. The offline demo stays explicit and isolated. See [mobile-backend-integration.md](mobile-backend-integration.md). Earlier “deferred” and “not yet migrated” notes below describe previous phases; web work is outside this release.

**Web phase 1 (25 October 2026):** The user has now authorized the separate Next.js web product. `web/` implements the restaurant dashboard and public guest/QR ordering frontend using an isolated browser-local demo world and demo identities. The original mobile prompt's prohibition on a separate web app no longer applies to this new scope. It does not connect production Firebase, Serverpod, PostgreSQL or PayPal. See `web-phase-1.md` and `web/README.md` for routes, design sources, run instructions and verification. The native mobile integration remains separate.

The 0.8 source pass enhances camera QR entry, guest/staff floor maps, photo-led menus, structured-text menu draft creation and menu readiness. It preserves local/connected separation. Per the user's request, tests and builds are deferred. See mobile-experience-enhancements.md for entry points and integration gaps.

The active scope is the complete mobile frontend prompt preserved in `COMPLETE_MOBILE_FRONTEND_PROMPT.txt`. It supersedes the initial browse-and-save-only scope. The original approved design handoff remains in `MOBILE_APP_DESIGN_SYSTEM_GUIDELINES.md`.

Raysto is an independent restaurant platform for rays.to, separate from Awhar. The Android/iOS frontend includes an isolated local demo with customers, owners, managers, waiters, kitchen staff and couriers sharing a persistent world on one installation. The connected account entry uses Firebase project raysto-38505 for Google/email identity, exchanges it for a Serverpod session and reads the live restaurant catalog, menus and current user's order history. The backend is deployed at api.rays.to on the user's AWS server with separate Raysto services and database roles; Awhar is preserved. Broader demo operations and checkout are not yet migrated. See firebase-integration.md, backend-setup.md and aws-backend.md for evidence and boundaries. The future Node.js web product and rays.to landing page are separate from the API; www redirects to the root. Native identity is com.gmrt.raysto.

The 0.6 payment foundation is reusable independently of restaurant rules: authenticated existing backend orders can use PayPal Sandbox through a shared coordinator/adapters/presentation layer. A separate, clearly labeled local test lab exercises recovery and error behavior without business records. This does not migrate the demo checkout or establish native payment acceptance; see paypal-mobile-core.md.

Version 0.7 adds standalone actual PayPal Sandbox USD1 checkout through the same coordinator, with separate receipts and capture/webhook evidence. It requires a connected account but no restaurant order. Deployed unapproved checkout, authorization and retry checks passed; buyer approval and native acceptance require the phone test. See paypal-real-sandbox-test.md.

Customers discover restaurants, build validated baskets, join explicit table visits, place local orders, inspect simulated payment/tracking states, request service and manage preferences. Restaurant teams use the same records for menu/service configuration, floor plans, orders, requests, deliveries, reservations, payments and reports. Identity and restaurant permissions are enforced in shared actions, not merely hidden controls.

The connected account now also supports Google identity. Personal Firebase preferences, private avatars and advisory presence have prepared clients and deployed security rules; Firestore, Storage and Realtime Database are provisioned in the user-selected Belgium region. Dedicated product screens and authenticated-user live CRUD are not claimed. See firebase-services.md. PostgreSQL retains restaurant permissions and commerce data.

Within the local demo, credentials, payments, emails, AI services, legal commitments, location and cross-device sync remain simulated. The connected account flow uses actual Firebase email actions and authenticated backend reads; it does not grant the demo's restaurant roles. The local assistant proposes actual current demo menu items and requires approval. The mock checkout freezes amounts and remains separate from preparation. The demo restaurant/menu content and photos are illustrative; unknown dietary information remains unknown.

The approved Material 3 paper/forest/lime foundation controls visual language. Native mobile components, semantic light/dark themes, bundled fonts, RTL, accessible scaling and meaningful interruptible motion are part of the product. Reference concept boards in `ui/` inform coverage only.

Implementation status and evidence are maintained in `implementation-checklist.md`, `screen-inventory.md` and `validation.md`. Tests and emulator checks do not establish production security or physical-device performance. A real product will need separately designed service integration, policies, identity, verified restaurant data, release signing and platform validation.
