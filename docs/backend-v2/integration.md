# API integration

The complete route list is [openapi.json](openapi.json). `backend/sdk/typescript/raysto-client.ts` is generated from the same source inventory. Dart commands are regenerated by the pinned Serverpod generator; generated files must not be edited by hand.

## Identity and headers

`POST /api/v2/auth/firebase` accepts `{"firebaseIdToken":"..."}` and exchanges verified Firebase identity for Serverpod authentication. `POST /api/v2/auth/guest` accepts `{"appCheckToken":"..."}` and creates an anonymous account. Their returned authentication envelope is the Serverpod `AuthSuccess` contract. These routes exist only when v2 is enabled. The existing generated Firebase and guest RPC endpoints remain available to Dart.

Authenticated requests send `Authorization: Bearer <Serverpod token>`. Registered v2 requests additionally send `X-Raysto-Firebase-Token: <current Firebase ID token>`. This is deliberately checked against the registered Firebase UID and revocation state; a refreshed backend session alone cannot bypass revoked Firebase identity. Guests send `X-Firebase-AppCheck`; new guest creation always requires a valid App Check token. Registered App Check starts in observation mode and can move to enforcement after client rollout.

Browser clients use an explicit HTTPS origin allowlist at the Raysto proxy. No wildcard CORS with credentials. Do not put identity tokens in URLs, analytics, logs or localStorage. The generated TypeScript client requests fresh headers through its credential callback and does not persist secrets. Guest recovery requires keeping the Serverpod authentication/refresh material in appropriate secure client storage; a new anonymous login creates a different guest.

Backend token existence is checked for protected v2 calls and live stream polls. `identity.stepUp` accepts a fresh Firebase token, checks recent authentication and the signed second-factor claim, and creates a five-minute grant bound to the current backend session. A grant from another device/session cannot authorize the caller. Ownership and payment settings use MFA; ordinary manager refunds require recent authentication.

## Commands

All effectful commands require a stable 16–100 character `requestKey` containing letters, digits, underscores or hyphens. Repeating the same payload returns its original result. Reusing the key with different input produces `idempotency_conflict`. Edits with a version require the last observed `expectedVersion`; stale writes return `version_conflict`.

Most administrative commands use this explicit envelope:

```json
{
  "requestKey": "menu-edit-unique-00001",
  "restaurantId": 12,
  "expectedVersion": 3,
  "dataJson": "{\"name\":\"Seasonal soup\",\"category\":\"Starters\",\"priceMinor\":850}"
}
```

Send it to `/api/v2/commands/menu.save`. `dataJson` is a JSON string because the same transport is used by Serverpod's generated Dart client. Unknown business fields are rejected by the command service. `resourceId` identifies an existing table, order, request, invitation or other command target. See the owning command's `_keys`, `_str`, `_int` and transition checks for the exact schema; the capability index links each operation to its implementation.

The critical commands use generated types: `CreateQuote`, `SubmitOrder`, `StartVisit`, `AllocatePayment`, `RequestRefund`. Corresponding REST paths are `quote.create`, `order.submit`, `visit.start`, `payment.allocate`, `payment.refund`.

```json
{
  "requestKey": "quote-request-unique-001",
  "restaurantId": 12,
  "fulfillment": "pickup",
  "linesJson": "[{\"productId\":41,\"quantity\":2,\"options\":[\"size:large\"],\"note\":\"\"}]",
  "tipMinor": 0
}
```

The response contains a quote ID, expiry and frozen totals. Submit that ID; never send an authoritative total from the client. Scheduled `slot` is an ISO timestamp with an explicit offset. Availability responses are advisory; submission repeats checks under the restaurant lock.

## Payments and receipts

1. `payment.allocate` chooses one visit or one non-visit order. For a visit, omit `amountMinor` and `lineKeys` for the whole remaining bill; supply exact `orderId:lineKey` keys for item units, or `amountMinor` for a custom amount. The methods are `paypal` and authorized staff `cash`.
2. Use `payment.checkout` with the resulting checkout as `resourceId`. Open only its provider approval URL.
3. After approval, call `payment.capture`; poll the `checkout` query if uncertain. A redirect is never proof of payment.
4. Cash uses the same reservations and ledger but records an immediate authorized collection. Refunds are requested by managers with recent authentication and processed durably.
5. Use `order`, `visit`, `checkout`, `report` and `payment.exceptions` reads for operational and financial state.

Example: a charge of 1,000 has 300 collected. Remaining debt is 700. Refunding 100 reduces collected money to 200 and adds a 100 credit, leaving debt 700. Cancelling the entire charge credits all 1,000; refunding collected money later leaves debt zero. Preparation status does not decide financial state.

An unknown provider outcome keeps its reservation. After the safe provider retry window, an operator reconciles provider history; the app must not create a replacement checkout or tell the customer they were not charged.

`merchant.connect` requires `dataJson: "{\"shareDataConsent\":true}"` after the owner explicitly consents. `merchant.refresh` reads provider evidence; caller-supplied merchant IDs never select a payment recipient. Subscription plans currently support a single indefinite monthly cycle with the configured final price, no trial/setup fee and no additional provider tax.

`admin.reconcileRefund` takes `restaurantId`, `resourceId` equal to the capture ID, and data containing `providerRefundId`, optional `localRefundId`, and an audit `reason`. Use it to attach a lost refund response to the existing local request, or import an external refund when no unresolved local request makes the mapping ambiguous. It verifies the provider refund's capture link, amount and currency before recording it, and never sends a new refund POST.

## Files and AI

`media.upload` creates an intent with purpose, MIME type, exact byte count and SHA-256. Upload the bytes with `PUT /api/v2/media/{id}/content` (8 MiB maximum). The asset remains private and quarantined. Approved assets can be read at `/api/v2/media/{id}` subject to ownership or publication. A menu image is publishable only after decoding and sanitized re-encoding. PDF originals remain private.

`ai.start` accepts `menuExtract`, `menuGenerate`, `translate` or `recommend`, a source `mediaId` and/or text, and locale. Poll `ai`. `ai.approve` binds the exact operation version and menu version. Reviewed import items become a menu draft; a separate `menu.publishDraft` publishes it. A basket proposal returns candidate lines for explicit cart merge and a fresh authoritative quote. AI never creates a payable order itself.

## Reads, streaming, reports and exports

Queries use `limit` 1–100 and monotonic `cursor` IDs. Discovery and service availability never reveal an occupied party. Staff projections omit unnecessary customer information; courier addresses are available only for assigned active deliveries.

Serverpod `platform.events` and REST `/events` publish authorized snapshot-invalidations with IDs. Reconnect using the last cursor and refresh a permitted query. These are bounded streams, not a financial ledger; snapshots are the authority. In-app notifications have their own stable event IDs.

Use `restaurantId=0` for the caller's private inbox events, and a positive restaurant ID for current staff invalidations. Both channels recheck access on each poll. `report=summary` returns booked sales, collections, refunds, commission, completed counts and current outstanding balances for orders in the selected range; these are distinct accounting measures. `admin.revenue` separates subscription collections/refunds and commission by currency.

Reports accept only predefined report names, tenant, UTC range (maximum 93 days), cursor and limit. AG Grid should map user actions to these fields; SQL strings, arbitrary sort/filter expressions and raw grid query objects are not accepted. Exports use authenticated private download paths, with expiry checks, rather than public storage URLs.

## Rooms and conversational assistance

The same authorization and command handlers serve generated Dart requests, generic REST commands, and additive resource aliases:

| Method and path | Purpose |
| --- | --- |
| `POST /api/v2/rooms/open` | Resolve the caller's authorized visit/order room |
| `GET /api/v2/rooms/{id}?restaurantId=…&before=…` | Bounded snapshot/history; table QR alone grants no access |
| `POST /api/v2/rooms/{id}/messages` | Send with a stable client message ID and optional same-room reply |
| `POST /api/v2/rooms/{id}/read` | Advance the caller's read cursor |
| `POST /api/v2/rooms/{id}/preferences` | Explicitly share preferences or mute suggestions |
| `POST /api/v2/assistant/runs` | Start a bounded run for an authorized room |
| `GET /api/v2/assistant/runs/{id}?restaurantId=…` | Status, sanitized tools, answer and reviewable proposal |
| `POST /api/v2/assistant/runs/{id}/cancel` | Cancel without publishing a late result |
| `POST /api/v2/assistant/proposals/{id}/approve` | Approve the exact expected proposal version |
| `GET /api/v2/operations/snapshot?restaurantId=…` | Current role-restricted operational records |
| `POST /api/v2/operations/layout` | Persist validated presentation state |

Writes retain the command envelope above. IDs in the route override body IDs. For example, a message body is:

```json
{
  "requestKey": "room-message-request-0001",
  "restaurantId": 12,
  "dataJson": "{\"clientMessageId\":\"phone-message-unique-0001\",\"text\":\"Could we have water, please?\"}"
}
```

Send it to `/api/v2/rooms/24/messages`. Its receipt means persisted delivery to the room, not staff acknowledgement. Reconnect using ordered sequences and refresh the authorized snapshot; never merge another identity's pending messages after logout. Authentication/current Firebase proof is required during streams as well as initial connection.

Exact split payments add `shares: [{chargeId, amountMinor, expectedVersion}]` and, where applicable, `assistantProposalId` to `AllocatePayment`. A frozen equal split records every participant's original share. The second payer does not pay half of the reduced remaining bill. One unresolved visit checkout prevents competing reservations; new rounds require another reviewed split. A proposal approval does not authorize another person's payment.

The console's custom AG Studio harness invokes `operations.assistant`. Its allowed presentation tools select filters/layouts only. Payment status includes the actual `paypal_mcp` or `paypal_rest` source; fallback must never be presented as successful MCP evidence.

## Source regeneration commands

After source-model or endpoint edits, use the Serverpod MCP if connected; the pinned bootstrap CLI fallback is `backend/backend.ps1 -Action generate`. `python backend/tools/export_platform_contracts.py` exports OpenAPI, the TypeScript client, dictionary and capability index. `backend/tools/export_system_maps.py` renders documentation diagrams. Neither exporter starts application services.
